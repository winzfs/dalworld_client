# DalWorld Client AI Workflow Guide

> AI 작업자는 클라이언트 코드를 수정하기 전에 이 문서를 먼저 읽고, 이 문서와 충돌하는 변경을 하지 않는다.

Last updated: 2026-05-20

## 1. 목적

이 문서는 DalWorld 클라이언트 저장소에서 AI가 헛수고하지 않고 일관된 방식으로 작업하기 위한 기준 문서다.

DalWorld 클라이언트는 Pixi.js v8 기반의 2D 멀티플레이 생존/건설 게임 클라이언트다. 클라이언트는 렌더링, 입력, UI, 미리보기, 서버 이벤트 반영을 담당한다. 실제 게임 판정과 월드 상태 확정은 서버 Durable Object가 담당한다.

## 2. 작업 전 반드시 확인할 문서

AI는 코드 수정 전에 아래 순서로 문서를 확인한다.

1. `README.md`
2. `docs/AI_WORKFLOW.md`
3. `docs/CURRENT_SYSTEM_STATUS.md`
4. `docs/ARCHITECTURE_GUIDE.md`
5. 관련 도메인 문서
   - `docs/isometric-building-system.md`
6. 실제 코드

문서와 코드가 충돌하면 코드를 기준으로 현재 동작을 확인하되, 문서도 함께 최신화해야 한다.

## 3. 절대 원칙

### 3.1 Pixi.js v8 기준

- Pixi.js는 v8 기준으로 작성한다.
- 오래된 Pixi v6/v7 방식의 API를 임의로 도입하지 않는다.
- 렌더링 객체 생성, 컨테이너 정렬, ticker 사용 방식은 현재 코드 스타일을 따른다.

### 3.2 클라이언트는 서버 권위 구조를 깨지 않는다

클라이언트가 해도 되는 것:

- 입력 수집
- 로컬 예측 이동
- 화면 렌더링
- UI 표시
- 건설 미리보기
- 서버 요청 전송
- 서버 snapshot/event 반영
- 편의상 배치 가능 여부를 예측 표시

클라이언트가 하면 안 되는 것:

- 아이템 획득 최종 확정
- 자원 채집 성공 최종 확정
- 건설물 배치 최종 확정
- 건설물 철거 최종 확정
- 몬스터 AI 최종 결정
- 전투 피해 최종 확정
- 사망/리스폰 최종 확정
- 서버가 거절한 상태를 실제 월드에 반영

## 4. 현재 클라이언트의 주요 책임

현재 클라이언트는 다음 기능을 가진다.

- Pixi.js v8 기반 렌더링
- WebSocket 연결과 자동 재연결
- 서버 snapshot 기반 플레이어/자원/몬스터 렌더링
- 클라이언트 로컬 예측 이동
- 입력 송신
- 카메라 follow
- HUD와 게임 창 UI
- 모바일 조이스틱과 모바일 버튼
- 월드맵 렌더링
- `?editor=1` 기반 맵 에디터 모드
- 건설 모드 UI
- 건설 그리드/고스트 미리보기
- 건설 배치/수정/철거 요청 전송
- 서버 건설 이벤트 반영
- 제작 요청 UI 연동

## 5. 코드 수정 기본 규칙

1. 기존 기능을 임의로 삭제하지 않는다.
2. 파일 하나에 기능을 계속 몰아넣지 않는다.
3. `GameApp.ts`에 새 로직을 추가하기 전에 독립 시스템으로 분리할 수 있는지 검토한다.
4. 서버 프로토콜을 바꾸면 서버 저장소의 프로토콜 타입과 문서도 같이 수정해야 한다.
5. UI만 바꾸는 작업과 게임 판정 변경 작업을 섞지 않는다.
6. 렌더링 로직과 네트워크 로직을 한 모듈에 섞지 않는다.
7. 클라이언트 예측 로직은 서버 판정과 불일치할 수 있음을 전제로 작성한다.
8. 서버 거절 이벤트를 반드시 처리한다.

## 6. 건설 시스템 작업 규칙

건설 시스템은 서버 권위 구조다.

클라이언트 작업 범위:

- 부품 선택
- 회전 선택
- 층 선택
- 마우스/터치 좌표를 건설 그리드로 변환
- 고스트 미리보기 표시
- 드래프트 편집
- 서버에 요청 전송
- 서버 이벤트 수신 후 렌더링 반영

클라이언트가 하면 안 되는 것:

- 서버 응답 없이 실제 건설물 추가
- 서버 응답 없이 인벤토리 재료 차감 확정
- 서버 응답 없이 충돌 맵 확정
- 서버 거절 후 드래프트를 실제 상태로 유지

건설 관련 수정 시 확인할 파일 예시:

- `src/game/GameApp.ts`
- `src/systems/building/*`
- `src/protocol/messages.ts`
- `docs/isometric-building-system.md`

## 7. 맵 에디터 작업 규칙

맵 에디터는 `?editor=1`에서만 활성화된다.

주의 사항:

- 일반 게임 모드와 에디터 모드의 입력 처리를 섞지 않는다.
- 에디터 전용 UI가 일반 게임 모드에 노출되지 않게 한다.
- 월드맵 저장 프로토콜을 바꾸면 서버의 `/maps/default` 계열 엔드포인트도 같이 확인한다.
- 대형 맵을 고려해 셀 기반 구조를 유지한다.

## 8. 프로토콜 작업 규칙

클라이언트 `src/protocol/messages.ts`는 서버와 호환되어야 한다.

프로토콜 변경 시 반드시 확인할 것:

- client `src/protocol/messages.ts`
- server `src/protocol/messages.ts`
- client 메시지 송신 코드
- server 메시지 처리 코드
- server snapshot/event 브로드캐스트 코드
- 관련 문서

프로토콜 변경은 하위 호환성을 고려한다. 기존 클라이언트가 받을 수 없는 필드를 추가할 때는 optional 필드를 우선 사용한다.

## 9. 성능 규칙

- 매 프레임마다 대량 객체를 생성하지 않는다.
- Pixi DisplayObject를 불필요하게 생성/삭제하지 않는다.
- 자주 바뀌는 렌더링은 재사용 가능한 객체 풀 또는 업데이트 방식으로 처리한다.
- snapshot 반영 시 전체 재생성보다 diff/update 방식을 우선한다.
- 모바일 성능을 고려한다.

## 10. 작업 후 체크리스트

AI는 작업 완료 전 아래 항목을 확인한다.

- [ ] Pixi.js v8 기준을 지켰는가?
- [ ] 클라이언트가 서버 권위 구조를 깨지 않는가?
- [ ] 기존 기능을 삭제하거나 약화하지 않았는가?
- [ ] `GameApp.ts`에 불필요하게 책임을 더하지 않았는가?
- [ ] 프로토콜 변경 시 서버 저장소도 같이 수정했는가?
- [ ] 건설/제작/채집/전투 판정을 클라이언트에서 확정하지 않았는가?
- [ ] 서버 거절 이벤트를 처리하는가?
- [ ] 모바일 입력과 데스크톱 입력을 모두 고려했는가?
- [ ] 타입 검사를 통과할 수 있는 구조인가?
- [ ] 관련 문서를 최신화했는가?

## 11. AI에게 주는 작업 방식 지침

작업 요청을 받으면 바로 코드를 덮어쓰지 말고 다음 순서로 진행한다.

1. 관련 문서 확인
2. 관련 코드 위치 파악
3. 현재 구조 요약
4. 변경 범위 확정
5. 서버 권위 원칙 위반 여부 검토
6. 최소 변경으로 구현
7. 타입/런타임 오류 가능성 검토
8. 문서 업데이트

불확실한 경우 임시방편으로 처리하지 않는다. 전체 구조에서 근본 원인을 찾아 해결한다.
